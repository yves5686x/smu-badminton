# 预约功能

## 概述

SMU Badminton 提供两种预约模式：**即时预约**和**定时预约**。两种模式共享相同的底层预约逻辑，但在执行时机和并发策略上有本质区别。

## 即时预约

即时预约在用户提交请求后立即执行，适合场地尚未被抢完的情况。

### 执行流程

```
POST /api/book
    |
    v
资源锁检查 --> 同一用户同一天是否已有预约
    |
    v
插入本地预约记录（防重复，UNIQUE 约束）
    |
    v
获取 Token（缓存或重新登录）
    |
    v
检查是否已有预约记录 --> 已有则跳过
    |
    v
查询资源 & 时间段 ID
    |
    v
前置校验（验证码要求 + 时段容量）
    |
    v
提交预约请求
    |
    v
预约失败则回滚本地预约记录
```

### 特点

- 单线程执行，一次预约尝试（请求级**不重试**，避免消耗账号的接口频控额度）
- 内置前置校验：检查资源是否需要预约验证码、时段容量是否充足
- 失败时自动回滚本地预约记录
- 同一用户同一天只能有一个预约（数据库 UNIQUE 约束保障）

### 前端异步路径（推荐）

页面上的「立即预订」走的是异步任务接口，而不是阻塞式的 `/api/book`：

```
POST /api/jobs/immediate   -->  毫秒级返回 job_id
        |
        v
格子进入 pending 态（琥珀色旋转沙漏）
        |
        v
后台线程执行与 /api/book 相同的完整链路
        |
        v
任务到达终态 --> 快轮询感知 --> 刷新网格展示真实结果并弹结果提示
```

- 与同步接口共享同一套前置校验：资源锁检查、一天一约拦截、本地占位记录写入
- 任务以 failed / skipped / cancelled 终结时自动回滚占位记录，不留"幽灵占位"
- 待结果期间使用 3 秒快轮询；全部待确认格清零后自动退回普通轮询

## 定时预约

定时预约在用户指定的目标时间点自动发起预约，支持多线程并发，适合抢热门时段。

### 执行流程

```
POST /api/book/schedule
    |
    v
资源锁检查 --> 同一用户同一天是否已有预约
    |
    v
插入本地预约记录
    |
    v
启动后台线程，立即返回 job_id
    |
    v
[长等待] 可中断等待至 T-75s
    |
    v
[对时校准] ClockSync 测量「网络-本地」时钟偏移（此后等待零 HTTP）
    |
    v
[登录] 获取 Token，并预检 JWT exp（临近过期则提前重新登录）
    |
    v
[预取] 一天一约检查 + 资源/时段 ID + user_info，全部复用同一条预热连接池
    |                              |
    | 预取拿到 ID                   | 预取未拿到 ID（上游 T-0 才放号，常见）
    v                              v
[验证码预取池] 已知需要则预热    [验证码预取池] 校验开关未知，投机预热
    |                              |
    +--------------+---------------+
                   v
[精确等待] 本地钟 + 偏移量走到 T-0（等待本身不发网络请求，必要时到点解析资源或重新登录）
    |
    v
[T-0 兜底] 若预取未拿到资源/时段 ID，现场解析一次（最多 3 次查询、间隔 0.15s，共享 4 秒查询预算）
    |
    v
[提交] 主线程统一启动最多 2 次提交，各带一份独立凭证（不重试、请求超时 4s）
    |
    v
任一成功 --> 跳过尚未发出的请求；等待已发出的请求结束
    |
    +-- 成功：任务置 done，保留本地预约记录
    +-- 失败：任务置 failed，并回滚本地预约记录
```

### 预取失败不等于任务失败

学校场地是「提前 7 天、每晚 21:00 放号」。因此 T-75s 的预取窗口里目标场次**尚未放出**，
`fetch_resource_time_id` 必然返回空——这是正常现象，不是故障。若在此处把任务判成 failed，
就会出现「到点了却一枪未发」的结果。

正确处理：预取失败只记录告警，转入 **T-0 兜底**——主线程到达目标时刻后统一解析
一次资源/时段 ID，拿到即立刻提交。多花一个 RTT，但至少开了一枪。

同理，预取失败时 `open_captcha_verify`（资源是否开启滑块校验）也是未知的。
由于滑块凭证只绑 token、不绑具体场次（`gen_slide_captcha(token)` 没有场次入参），
此时会**投机预热**验证码池：若随后确认不需要校验，这些凭证被丢弃即可；
若确实需要，T-0 就直接有凭证可用，避免临阵解滑块（数秒，等于放弃抢票）。

### 失败必须回滚本地预约记录

`local_bookings` 的作用有两个：当天冲突判定的依据、前端格子「已占用」的来源。
它的唯一约束是 `(bookdate, resources_name, kssj, jssj)`——**按场次唯一**，不带用户名。

所有预约入口由 `BookingService` 统一检查并创建占位，任务保存对应的 `local_booking_id`。
任务结束时由 `BookingStore.transition()` 在同一事务中更新状态并释放失败任务的占位。
删除按记录 ID 定位，旧任务不会误删同一场次后来创建的记录；成功任务保留占位。
旧脚本的 `rollback_local_on_fail` 仅作兼容，Web 入口使用明确的记录归属。

### 可中断等待

长等待使用 `Event.wait()`，取消事件能立即唤醒；粗等待每次最多 60 秒。
进入预取窗口后用 `ClockSync` 校时，最终对齐使用校准时钟。
没有网络校时结果时仍可依靠本地时钟前进，不会无限卡在粗等待阶段。

### 目标时间计算

目标时间 = `bookdate - 7 天 + target_time_str`

例如：预约 2025-12-18 的场地，目标时间为 21:00:00，则系统将在 2025-12-11 21:00:00 自动发起预约。

> 学校系统通常在预约日期前 7 天开放预约权限，因此定时预约的执行时间即为开放抢场的时间点。

### 并发枪数与上限

- 实际开火枪数 = `min(num_threads, MAX_UPSTREAM_BURST=2)`：上游对预约接口按账号限流，
  历史测试曾观察到第 3 发触发「频繁调用接口，禁用 3 分钟」。当前设置为最多 2 次提交，成功后跳过尚未发出的请求
- 所有枪通过 `threading.Barrier` 对齐（超时 20 秒）
- 滑块验证码为**一次性凭证**（实测同一凭证第二次提交返回「验证码不能重复使用」），
  因此每枪自带独立凭证，优先在预取窗口内解好；晚建任务或重登后限次补准备，解码失败不裸提交
- 任一枪成功即触发停止标记，其余枪不再提交
- 提交结果记录业务响应分类；频控封禁在日志中标为 `banned`

### 运行模式

统一走后台任务执行，立即返回 `job_id`。历史字段 `run_async` 仅为兼容旧客户端保留，
当前版本不再区分同步路径。

## 任务状态机

定时预约任务遵循严格的状态机规则：

```
scheduled --> running --> done
    |           |-------> failed
    |           |-------> skipped
    |           |-------> cancelled
    |-------> cancelled
```

| 状态 | 说明 | 类型 |
|------|------|------|
| `scheduled` | 已创建，等待执行 | 非终态 |
| `running` | 已到目标时刻，正在解析资源或提交 | 非终态 |
| `done` | 预约成功 | 终态 |
| `failed` | 预约失败 | 终态 |
| `skipped` | 已有预约，跳过 | 终态 |
| `cancelled` | 已取消 | 终态 |

终态不可被覆盖，状态转换必须合法。

## 取消预约（真实撤销学校侧）

取消入口为 `POST /api/jobs/stop_by_params`，除停止本地排队任务外，还会尽力撤销学校侧已生效的预约：

1. 向活跃任务发送取消信号，由执行器确认终态；尚在提交时返回 `pending`。
2. 等任务结束后，查询学校侧匹配预约 ID，依次调用
   `checkAppointmentCancelTime` → `updateAppointmentInformationState(state="1")`。
3. 学校侧确认取消成功或确认不存在时释放对应本地记录；查询或取消失败时保留已成功预约的本地记录。

凭据来源两级兜底：优先使用请求携带的 `access_token`；未提供则尝试用服务端保存的账号静默重新登录。
若两者都不可用，仅停止排队，无法确认学校侧结果的记录会保留，并在结果中明确说明。

响应中的 `upstream_status`：

| 值 | 含义 |
|----|------|
| `pending` | 取消信号已发出，等待正在执行的请求结束；稍后确认并按需再次取消 |
| `cancelled` | 学校侧预约已成功撤销 |
| `none` | 学校侧没有匹配时段的有效预约 |
| `skipped` | 无可用凭据，仅取消了本地排队 |
| `failed` | 上游拒绝或异常，`message` 携带原因与预约 ID |

## 并发占位

冲突检查和占位插入在一个 SQLite 写事务中完成，同一用户同日以及同一场次的并发请求共享此约束。
不再额外维护按资源分配的 asyncio 锁与清理任务。

## 任务持久化

所有预约任务会持久化到 SQLite 的 `scheduled_jobs` 表：

- 服务重启后自动调用 `load_pending_jobs()` 恢复待执行任务
- 密码以混淆方式存储（XOR + Base64）
- 历史任务定期清理（保留期由 `JOB_RETENTION_SEC` 控制，默认 3600 秒）

## 内置调优常量

抢票节奏相关的常量集中在 `src/smu_badminton/cas_manager.py` 顶部（2026-08-27 对上游实测定案）：

| 常量 | 默认值 | 说明 |
|------|--------|------|
| `MAX_UPSTREAM_BURST` | 2 | 开火枪数硬上限（受上游每账号频控约束） |
| `PREFETCH_WINDOW_SEC` | 75 | 距目标时刻多少秒唤醒进入预取窗口 |
| `CAPTCHA_HARD_STOP_BEFORE_SEC` | 35 | 验证码池构建最晚截止点 |
| `RUSH_REQUEST_TIMEOUT_SEC` | 4 | 抢票请求超时（单发快断） |
| `TOKEN_EXP_BUFFER_SEC` | 120 | 会话 exp 距目标不足该值时提前刷新（经 `session_exp_epoch` 读取，access_token 读不出时回退 id_token） |
| `T0_RESOLVE_RETRIES` | 3 | T-0 兜底解析资源/时段 ID 的重试次数 |
| `T0_RESOLVE_BUDGET_SEC` | 4 | 到点资源解析共享查询预算（秒），超时结果不用于提交 |
| `T0_RESOLVE_GAP_SEC` | 0.15 | T-0 兜底解析的重试间隔（秒） |
